## Arquitectura

- `core`: contratos existentes `AuthRepository`, `SessionStore`, `RestoreSessionUseCase`; casos de uso login/logout, errores tipados, cuatro roles y política de permisos.
- `app/shared`: adaptador HTTP, controlador central con exclusión de operaciones simultáneas y UI Compose. El backend decide identidad, rol y permisos. La UI no pide un rol.
- `server/auth`: servicio, puerto transaccional e implementación JDBC sobre Hikari/MySQL. Composición manual desde `Application.module`.
- El Commit 01 no añadió módulos. El ciclo de plataforma incorpora `app/webApp`, reutilizando core/shared y composición manual. Ningún cliente se conecta a MySQL.

## API

Todas las respuestas usan `ApiEnvelope`. Los cuerpos de autenticación y sus cabeceras no se registran. No se siguen redirecciones HTTP en el cliente.

| Método/ruta | Entrada | Resultado |
|---|---|---|
| POST `/api/v1/auth/login` | `username`, `password` | Usuario, rol, permisos y par de tokens |
| POST `/api/v1/auth/refresh` | `refreshToken` | Nuevo par de tokens; invalida el anterior |
| POST `/api/v1/auth/logout` | `refreshToken` | Revoca la familia; idempotente |
| GET `/api/v1/auth/me` | `Authorization: Bearer …` | Identidad actual, rol y permisos de la base |
| GET `/api/v1/auth/permissions/{permission}` | Bearer; `providerId` para `PROVIDER_HOME` | Comprueba permiso y propiedad; no devuelve datos de negocio |

La ruta de permisos es un contrato mínimo verificable, no un módulo administrativo ni una API de datos del proveedor. Futuros endpoints deben aplicar la misma autorización a la operación y filtrar los datos por propietario en el servidor; consultar esta ruta desde la UI no sustituye esas comprobaciones.

Errores: `VALIDATION` (400), `INVALID_CREDENTIALS` (401), `UNAUTHORIZED` (401), `SESSION_EXPIRED` (401), `SESSION_REVOKED` (401), `ACCOUNT_BLOCKED` (403), `FORBIDDEN` (403), `UNAVAILABLE` (503). Usuario inexistente y contraseña incorrecta producen la misma respuesta. El bloqueo solo se informa después de verificar la contraseña.

Sin base configurada, `/health` sigue disponible y autenticación devuelve 503. `/health/db` abre una conexión y comprueba `isValid`, no solo la existencia del pool.

## Contraseñas y sesiones

PBKDF2-HMAC-SHA256 de JCA: 600000 iteraciones, salt aleatorio de 16 bytes, resultado de 256 bits, comparación mediante `MessageDigest.isEqual`. Los hashes incluyen versión y coste. Las cuentas nuevas requieren 12–256 caracteres; el login admite hasta 256 para no truncar contraseñas. Se realiza una derivación ficticia cuando no existe la cuenta.

Tokens opacos de 32 bytes aleatorios, generados con `SecureRandom` y codificados Base64URL. Solo sus hashes SHA-256 llegan a MySQL. Acceso: 15 minutos; familia: 7 días como límite absoluto, sin extenderse con renovaciones. No son JWT y **no necesitan secreto de firma**. Si se adopta firma en otro incremento, sus secretos deberán proceder del entorno.

La renovación es transaccional, conserva el historial y rota acceso y refresh. Reutilizar un refresh ya revocado revoca toda su familia. Una respuesta de renovación perdida puede obligar a iniciar sesión otra vez: se prioriza impedir replay. Logout invalida inmediatamente los tokens de la familia. Cada petición protegida consulta cuenta activa y rol actual. Bloquear una cuenta invalida sus siguientes accesos; no se confía en el rol almacenado por el cliente.

El cliente valida al arrancar y cada 60 segundos mientras muestra una raíz protegida. Solo renueva ante acceso expirado/no autorizado; no renueva una cuenta bloqueada ni una sesión revocada. Ante red no disponible conserva el almacenamiento y muestra reintento sin habilitar una raíz protegida. Logout elimina el estado local incluso si falla la red, e informa que no pudo confirmar la revocación remota. En ese caso la caducidad absoluta sigue limitando la sesión remota.

La navegación depende exclusivamente del estado central; no hay pila de pantallas protegidas a la que volver después del logout. Las cuatro raíces anuncian honestamente sus funciones futuras.

## Almacenamiento por plataforma

| Plataforma | Adaptador | Límite |
|---|---|---|
| Android | `AndroidSessionStore`: AES-256-GCM, clave no exportable en Android Keystore, escritura atómica en `noBackupFilesDir`; backup deshabilitado | Necesita prueba real en dispositivo/emulador |
| Windows Desktop | `WindowsSessionStore`: DPAPI del usuario actual, archivo cifrado y reemplazo atómico bajo LOCALAPPDATA/Ecolactea | Depende del perfil Windows; no portable a otro usuario |
| Desktop macOS/Linux | `MemorySessionStore` | Sin persistencia entre procesos; pendiente Keychain/Secret Service |
| iOS | `MemorySessionStore` | Pendiente Keychain y validación desde macOS; no probado en Windows |
| Web Wasm/JS | `MemorySessionStore` por pestaña | Sin persistencia al recargar; pendiente sesión con cookie HttpOnly, Secure y SameSite más defensa CSRF. No se escriben tokens en almacenamiento Web |

La contraseña solo permanece transitoriamente en memoria durante el envío; no usa estado guardable de Compose. Los modelos con secretos redactan `toString`. Archivos dañados o que no pueden descifrarse se descartan y requieren nuevo login.

## MySQL y Flyway

`V1__technical_foundation.sql` permanece intacta. `V2__authentication_sessions.sql` restringe el catálogo a los cuatro roles, valida el booleano de actividad y crea `auth_session`, con claves foráneas, hashes únicos, familia, expiración, revocación e índices. Se requiere MySQL 8.0.16+ para CHECK (el servicio local detectado es MySQL 8.4).

No hay cuentas ni contraseñas de ejemplo en las migraciones. Flyway aplica V2 al arrancar con `DB_URL` configurada.

## Configuración externa y bootstrap

| Variable | Uso |
|---|---|
| `ECOLACTEA_CONFIG_FILE` | Archivo local ignorado KEY=value; entorno prioritario |
| `WEB_ROOT` | Directorio público del artefacto Web generado, nunca carpeta de secretos |
| `DB_URL`, `DB_USER`, `DB_PASSWORD`, `DB_POOL_SIZE` | Configuración existente de MySQL |
| `SERVER_HOST`, `SERVER_PORT` | Configuración existente de escucha |
| `AUTH_BOOTSTRAP_ENABLED=true` | Habilita explícitamente el bootstrap |
| `AUTH_BOOTSTRAP_USERNAME`, `AUTH_BOOTSTRAP_PASSWORD` | Cuenta administrativa inicial; sin valores predeterminados |
| `ECOLACTEA_API_URL` | URL Desktop |
| Propiedad Gradle `ecolactea.apiBaseUrl` | URL Android en `BuildConfig`; configurar al ensamblar |

Bootstrap crea únicamente el primer `ADMINISTRADOR_GENERAL` cuando la base no tiene usuarios. Un bloqueo de fila del catálogo de roles serializa el bootstrap. Si ya existe cualquier usuario, no crea otro, aunque cambie el nombre configurado. Nunca cambia contraseñas existentes. Desactivar y retirar las variables de bootstrap después del primer arranque. Introducir secretos mediante configuración local protegida; no pegarlos en documentación, Git ni argumentos de comandos compartidos.

Producción requiere HTTPS mediante terminación TLS y red privada entre proxy y Ktor; no desplegar el listener HTTP directamente a Internet. Android release conserva la prohibición de tráfico claro; el manifest debug lo habilita solo para desarrollo. Para emulador Android, configurar la URL local con la propiedad Gradle. iOS mantiene las restricciones de transporte del sistema.

## Adaptadores pendientes: decisión técnica

- iOS: implementar `SessionStore` con Security.framework/Keychain (`SecItemCopyMatching`, `SecItemAdd`, `SecItemUpdate`, `SecItemDelete`), acceso restringido al dispositivo. Requiere validar interoperabilidad, entitlements y reinstalación en macOS/Xcode; no se puede certificar desde Windows.
- macOS Desktop JVM: puente nativo a Keychain; no pasar tokens como argumentos de procesos. Requiere prueba en el perfil/macOS real.
- Linux Desktop JVM: Secret Service/libsecret mediante el bus de sesión y un almacén desbloqueado. Una instalación sin servicio debe quedar sin persistencia, nunca degradarse a archivo plano. Requiere probar escritorio, bloqueo y ausencia del servicio.
- Web: la solución prevista es refresh en cookie HttpOnly/Secure/SameSite y acceso en memoria, con validación de Origin/CSRF para operaciones que usan cookies y rotación controlada entre pestañas. Esa ampliación no está implementada; el navegador actual pierde la sesión al recargar. No usar SQLite ni claves de cifrado persistidas junto al token para fingir protección.

Estas limitaciones mantienen RF-34 parcial en las plataformas requeridas. La compilación KMP de metadatos nativos no equivale a ejecutar esos adaptadores.
